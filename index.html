Experiment 1 · Midstate reuse vs full double SHA-256

Fresh random 80-byte headers. Same headers and nonces for every method. Baseline = generic double SHA-256 (3 compressions + padding/alloc per nonce). Optimized = cache SHA-256 state after the first 64 bytes, then per nonce: 2nd inner chunk (16 bytes + padding) + outer SHA-256 of the 32-byte digest = 2 compressions. Fair baseline = same code without caching (3 compressions). Ideal compression-count ratio: 1.5×.

Three questions tested so far ⇒ any p-value is compared with α = 0.05/3 ≈ 0.017 (Bonferroni). “No measurable advantage” is a valid result.
Q1 · Can we do the same work more efficiently?

Hypothesis: Reusing unchanged work (midstate, AsicBoost, version rolling) cuts compute per useful header hash.

Prior research: Midstate is standard since early GPU/FPGA miners; the host computes it once per job and the ASIC only varies the nonce. Bitaxe ASICs (BM1370 in Gamma 601) receive the midstate/job from AxeOS (ESP-Miner). AsicBoost (Hanke 2016): find several header variants whose first 64-byte chunk differs but whose last 4 bytes of merkle root collide, so the second-chunk message schedule is shared — saves ~20–30% of compute inside the chip. Overt AsicBoost = version rolling (BIP 320 bits, Stratum mining.configure version-rolling, BIP 310): the chip/firmware rolls version bits to produce multiple midstates cheaply. AxeOS already enables version rolling for BM13xx chips. Repeated work across workers: pools/stratum give unique extranonce1, so overlap is avoided by protocol; duplicate search only arises from misconfiguration.

Test: Exp 1 (above) + version-roll demo below (changing version bits changes the first chunk ⇒ new midstate, verified by independent hash).

Result: See Exp 1. Midstate is a real, already-captured saving; it gives a Bitaxe owner nothing new.

What would disprove it: optimized hashes differing from baseline (correctness), or speedup ≤1.0× on the fair baseline over repeated rounds.

Uncertainty: JS timing varies with JIT warm-up, thermal throttling, Low Power Mode; we report median and range over rounds and discard the first round as warm-up. Phone results say nothing about joules/TH. Missing measurement: Bitaxe J/TH with version rolling on vs off needs the ASIC + a wall-power meter (W at the plug) and AxeOS hashrate over ≥1 h each.

Q2 · Can we recover work that gets wasted?

Hypothesis: Stale jobs, Wi-Fi drops and slow block switches waste a meaningful fraction of a Bitaxe's hashes.

Prior research: Pools report stale/reject rates typically <1% on good links; block-switch latency is usually under 1 s with stratum clean_jobs. Each second of delay after a new block wastes ≈ 1/600 of expected block time.

SIMULATED model: useful H/s = H × (1−stale) × (1−downtime/1440) × (1−delay/600)

What would disprove it: measured AxeOS rejects <0.5% and uptime >99.5% ⇒ total recoverable <1%, i.e. nothing worth chasing.

Uncertainty: model is multiplicative/independent; real losses correlate (Wi-Fi drop ⇒ stale). Solo odds are a Poisson expectation, not a forecast.

Q3 · Can any strategy pick better candidates?

Hypothesis (to be rejected by default): nonce patterns, timestamp choices, or "AI-selected" nonces find valid hashes faster than sequential search.

Prior research: SHA-256d output is pseudorandom; any nonce/timestamp has the same probability ≤ target. Apparent patterns in historical winning nonces come from hardware search order (e.g. chips splitting nonce space), not from the hash.

Pre-declared metric: shares (hashes ≤ easy target, 12 leading zero bits) per hash spent, where prediction cost is counted in hash-equivalents. Fresh random headers each trial, equal budget per strategy, 30 trials, independent verifier re-hashes every share with the generic path. Test: two-sided z-test on rate vs baseline, Bonferroni α = 0.05/3.
